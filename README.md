# Bus Bunching Prediction via Early Warning Signals in a Transit Digital Twin

GTFS-RT data pipeline and predictive framework for bus bunching early warning signals, using San Francisco Muni data. Submitted to **PeerJ Computer Science** as an AI Application article.

## Overview

This project implements an end-to-end pipeline that:

1. **Collects** real-time GTFS-RT feeds (VehiclePositions + TripUpdates) from the 511.org API
2. **Stores** observations in DuckDB (embedded columnar analytics)
3. **Computes** three metrics: headway deviation, delay drift, and bunching index
4. **Predicts** bus bunching transitions using a multi-stop sequential window ($n-3$) with LightGBM and temporal hold-out validation

Current reproducible results are generated by `scripts/analyze_longitudinal.py` and written to `professor_metrics.txt`.

## Methodology

The predictive pipeline follows four stages:

1. **Data Ingestion**: GTFS-RT Protocol Buffer feeds (`VehiclePositions` + `TripUpdates`) are fetched from the 511.org API at 130-second intervals and parsed into tabular format.
2. **Preprocessing & Feature Engineering**: Raw AVL records are deduplicated, temporally ordered, and filtered for lag validity. DuckDB window functions compute inter-vehicle headways, delay differentials, and physics-informed ratio features across a 3-stop sequential window ($n-3$), producing a 24-dimensional feature vector per observation.
3. **State-Transition Modeling**: A LightGBM gradient boosting classifier, trained exclusively on onset transitions ($B_{n-1}=0$), predicts whether bunching will occur within the next 3 stops. Class imbalance is handled via `scale_pos_weight`, and the decision threshold is optimized on a held-out calibration set.
4. **Conformal Prediction**: A split conformal prediction layer converts point predictions into prediction sets with statistical coverage guarantees, providing operators with calibrated confidence levels.

Evaluation uses strict temporal hold-out (no random splits) and spatial cross-validation across independent routes.

## Project Structure

```
src/pipeline/
  collector/     Fetcher, parser, validator, runner (GTFS-RT ingestion)
  storage/       DuckDB store, snapshots (persistence)
  analysis/      Headway, delay drift, bunching (metrics)
  visualization/ Publication-ready plots
  config/        Settings (pydantic-settings, .env)

scripts/
  collect.py               Collect one GTFS-RT snapshot
  download_longitudinal.py  Download longitudinal dataset from Zenodo
  ingest_longitudinal.py    Ingest multi-month longitudinal data into DuckDB
  analyze_longitudinal.py   Run full analysis pipeline (training, evaluation, metrics)
  generate_pr_curve.py      Generate Precision-Recall curve figure

manuscript/
  english/       PeerJ submission (LaTeX + figures)
  spanish/       Spanish version

systemd/         Service + timer for continuous collection
tests/           Unit and integration tests
```

## Dataset Information

[![DOI](https://img.shields.io/badge/DOI-10.5281%2Fzenodo.19673388-blue)](https://doi.org/10.5281/zenodo.19673388)

- **Source**: San Francisco Municipal Railway (SF Muni) GTFS-RT feeds via [511.org Open Data API](https://511.org/open-data/transit), operated by the Metropolitan Transportation Commission (MTC)
- **Endpoints**: `VehiclePositions` and `TripUpdates` for agency `SF`
- **Period**: January–March 2026
- **Raw volume**: ~100,000,000 AVL updates
- **Processed volume**: 3,709,358 valid stop-level observations; 3,365,543 lag-valid records for sequential modeling
- **Routes**: 14 (Mission St), 38 (Geary Blvd), 49 (Van Ness Ave)
- **Format**: DuckDB database files (`.duckdb`), generated from Protocol Buffer binary feeds
- **Archived**: [Zenodo (DOI: 10.5281/zenodo.19673388)](https://doi.org/10.5281/zenodo.19673388)

## Code Information

The codebase is organized as a Python package (`src/pipeline/`) with CLI scripts under `scripts/`. Key components:

| Module | Description |
|--------|-------------|
| `src/pipeline/collector/` | GTFS-RT feed fetcher, protobuf parser, data validator |
| `src/pipeline/storage/` | DuckDB storage layer with snapshot management |
| `src/pipeline/analysis/` | Headway, delay drift, and bunching index computation |
| `src/pipeline/visualization/` | Publication-ready matplotlib/seaborn figures |
| `scripts/analyze_longitudinal.py` | Main analysis script: training, evaluation, all paper metrics |
| `scripts/generate_pr_curve.py` | Precision-Recall curve generation |

## Requirements

### System

- Python 3.11+
- [uv](https://github.com/astral-sh/uv) package manager
- 511.org API key ([register here](https://511.org/developers)) — only needed for live data collection

### Dependencies

Core libraries (pinned versions used in the paper):

| Library | Version | Purpose |
|---------|---------|---------|
| DuckDB | 1.5.1 | Embedded columnar analytics and feature extraction |
| LightGBM | 4.6.0 | Gradient boosting classifier |
| XGBoost | 3.2.0 | Baseline comparison model |
| scikit-learn | 1.8.0 | Logistic regression, Random Forest, metrics, preprocessing |
| Pandas | 3.0.2 | Data manipulation |
| NumPy | 2.4.4 | Numerical computation |
| Matplotlib | 3.10.8 | Publication figures |
| Seaborn | 0.13.2 | Statistical visualizations |
| SciPy | 1.12+ | Statistical tests (ADF, confidence intervals) |
| statsmodels | 0.14+ | Time series diagnostics |
| httpx | 0.27+ | HTTP client for API requests |
| protobuf | 4.25+ | GTFS-RT Protocol Buffer deserialization |

All dependencies are declared in `pyproject.toml` and resolved via `uv.lock`.

## Usage Instructions

### Setup

```bash
# Install dependencies
uv sync --all-extras

# Configure API key (only for live collection)
cp env.example .env
# Edit .env and set your API_KEY
```

### Collect Data (Live)

```bash
# Single snapshot
uv run python scripts/collect.py

# Continuous collection (systemd timer, every 130s)
bash scripts/install-timer.sh
```

### Reproduce Paper Results

```bash
# 1. Download historical dataset from Zenodo
uv run python scripts/download_longitudinal.py --start-month 2026-01 --end-month 2026-03

# 2. Ingest into longitudinal DuckDB view
uv run python scripts/ingest_longitudinal.py

# 3. Run full analysis (training + evaluation + all metrics)
uv run python scripts/analyze_longitudinal.py

# 4. Generate Precision-Recall curve figure
uv run python scripts/generate_pr_curve.py
```

Results are written to `professor_metrics.txt` and figures are saved to `manuscript/english/`.

### Tests

```bash
uv run pytest
uv run ruff check src/ tests/
```

## API Constraints

- 511.org rate limit: 60 requests/hour
- Each cycle: 2 requests (VehiclePositions + TripUpdates)
- Polling interval: 130 seconds
